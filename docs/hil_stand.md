# Теоретичний HIL-стенд для SENTRY SWM-2

Зараз стенд ручний: ESP32-S3 DevKit + HC-SR04 + реле + RGB LED + кнопки K1–K4, усе керується людиною через UART. Тут описано, як це можна перетворити на HIL-стенд, де стимули подає не оператор, а test-агент, а CI запускає весь прогін сам.

Фізично зібрано лише сам DUT і периферію — стимулятори (сервопривід, оптрони на кнопки, керована розетка) не збирались, це наступний теоретичний крок. Опис спирається на реальні обмеження, які вилізли під час тестування: HC-SR04 потребує активного заміру, Guard має часові вікна, і так далі.

## 1. Схема

```mermaid
flowchart TB
    subgraph PC["Test controller (ПК/Raspberry Pi)"]

        CI[CI runner<br/>self-hosted]

    subgraph HIL["HIL-стенд"]

        OBS_LA[Логічний аналізатор<br/>GPIO4, GPIO8, TRIG/ECHO]

    end

    TA -- керування --> STIM_D
    TA -- керування --> STIM_B
    TA -- керування --> STIM_W

    PWR -- USB power cut --> DUT

    AP --- SRV
    TA -- HTTP --> SRV
```

## 2. Компоненти

| Вузол | Навіщо | Як |
|---|---|---|
| DUT (ESP32-S3) | об'єкт тестування | UART 115200 8N1, вже є в `framework/drivers` |
| Test controller | виконує pytest, подає стимули, збирає докази | той самий `framework/` |
| Керування живленням | power loss / power cycle, OTA-9 | реле на лінії живлення DUT, кероване контролером |
| Стимулятор відстані | подати відстань до HC-SR04 без руки | сервопривід з перешкодою або генератор імпульсів на ECHO |
| Стимулятори кнопок | натискання/утримання без оператора | оптопари на GPIO41/40/39/38 |
| Керована точка доступу | детермінований обрив Wi-Fi для OTA-16, WF-5 | розетка з реле на живлення роутера |
| Логічний аналізатор | перевірка GPIO4/GPIO8 напряму | sigrok/Saleae на GPIO4, GPIO8, TRIG/ECHO |
| Камера / фотодатчик | об'єктивна перевірка кольору/патерну LED | USB-камера + OpenCV, зараз це робиться очима |
| Мультиметр | контроль напруг | перед першим увімкненням і за потреби |
| Локальний OTA-сервер | fault-injection | вже є, `fw_7/tools/ota_server.py` |

## 3. Чому саме такі стимулятори

HC-SR04 не моніторить нічого у фоні — ми переконались у цьому на практиці, коли жодна подія (alarm, collision, intrusion) не спрацьовувала без явного `distance`/`distance log`. Тому стимулятор відстані має бути синхронізований з тест-агентом: спершу запускаємо `distance log`, потім рухаємо перешкоду.

Guard має часові вікна (10 с arming, 15 с до ALARM), тож стимулятор має вміти витримати точний момент, щоб перевірити межу вікна, а не просто спрацювати "колись".

Кнопки відрізняють короткий press від hold (1.5 с) і від комбінацій (2 с) — оптопара має керуватись тривалістю імпульсу.

GPIO4 окремо вартий логічного аналізатора: саме тут ми зіткнулись з розбіжністю монтажу й задуманої полярності. З апаратним контролем рівня це виявилось би одразу на першому прогоні, а не через кілька днів ручного спостереження.

## 4. Безпека

- Живлення на DUT — через струмообмежене джерело.
- Перед будь-якою новою комутацією — перевірка continuity без подачі живлення.
- Реле стимуляторів за замовчуванням у стані "не заважати" (нормально замкнені), щоб збій контролера не лишив DUT без живлення посеред запису.
- Жоден стимулятор не подає напругу вище задокументованої — 3.3 В логіка ESP32, 5 В лінії (Echo HC-SR04) лише через рівневий перетворювач.
- Emergency stop — окрема фізична кнопка на лінії живлення, незалежна від test-агента.

## 5. CI/CD

```text
git push → self-hosted runner (ПК зі стендом)
  → health-check стенда
  → erase-flash + прошивка потрібної версії
  → smoke → functional + boundary
  → OTA fault-injection (тепер без ручного вимкнення Wi-Fi — розетка керована)
  → Guard/Alert сценарії з точним таймінгом
  → збір артефактів: логи, транскрипти, знімки аналізатора, фото LED
  → публікація звіту, оновлення results.json і traceability.md
```

Runner має бути self-hosted, не хмарний — тести торкаються реального заліза. `gen_traceability.py` вже вміє будувати матрицю з `results.json`, тож у CI це просто ще один крок.

## 6. Що автоматизується, а що ні

| Категорія | На HIL-стенді |
|---|---|
| Коди помилок, межі, OTA-логіка | повністю (вже зроблено в `framework/tests`) |
| GPIO4/GPIO8 напряму | повністю, логічний аналізатор замінює очі |
| Відстань HC-SR04 | повністю, сервопривід/DAC замінює руку |
| Кнопки, комбінації, дребезг | повністю, оптопари з точним таймінгом |
| Колір і режим RGB LED | частково — камера впізнає колір і базовий патерн, але не "чи гарно виглядає" |
| Обрив Wi-Fi у потрібний момент | повністю, розетка керована |
| Клацання реле (звук) | непрямо, через GPIO8, а не на слух |
| Глибина/тиск/вологість (симулятор) | не застосовується, PRD каже — модельні значення, на логіку не впливають |

## 7. Що в курсовій, а чого нема

У цьому проєкті зібрано тільки ручний стенд. Усі стимули в автотестах подаються програмно через UART, без фізичних стимуляторів — для функціонального і межового тестування цього достатньо, але не для того класу дефектів, що знайшовся лише вручну: невідповідність монтажу GPIO4 і текст одиниці виміру в BUG-009. Саме ці два випадки і є аргументом, чому HIL з логічним аналізатором і камерою вартий окремого кроку — вони прибирають останню частину тестування, що лишається повністю ручною.
