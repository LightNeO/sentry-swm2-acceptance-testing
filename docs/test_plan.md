# Тест-план: приймальні випробування SENTRY SWM-2 (fw_7)

| | |
|---|---|
| Продукт | SENTRY SWM-2 — модуль гідроакустичної вахти (навчальна збірка на ESP32-S3) |
| Версії під тестом | **2.1.0** (stable) і **2.3.0** (beta) |
| Мета | Вирішити, чи можна 2.3.0 перевести з beta у stable (GO / NO-GO / CONDITIONAL) |
| База тестування | Тільки `fw_7/PRD.md` (див. `docs/requirements.md`) |
| Автор | Антон Єрьомін |
| Статус | Виконано (вердикт: `docs/verdict.md`) |

## 1. Scope

### 1.1. У scope

- Усі функціональні вимоги PRD (розділи 2–13): доступ/стани, Wi-Fi, акаунт, OTA, лампа, реле, сонар, health, Guard, Alert center, кнопки, система.
- Межі всіх числових діапазонів (мін-1 / мін / макс / макс+1).
- Збереження в NVS після reboot і після OTA (OTA-10).
- Регресія 2.1.0 → 2.3.0 (NFR-1): весь функціонал 2.1.0 повторно на 2.3.0.
- OTA-сценарії: успіх, rollback, даунгрейд, помилки сервера/мережі/образу, відновлення після помилок.
- Дослідницьке тестування: приховані команди, секрети, безпека.

### 1.2. Поза scope

- Фонова телеметрія симулятора (`[NAV]`, `[ACU]`, `[PWR]`, `[HW]`) і `W`-повідомлення без коду — за PRD не баги.
- Реальні датчики глибини/тиску/батареї (відсутні на стенді).
- Функціонал 2.3.0 у версії 2.1.0 (`E099 planned in v2.3.0` — очікувано).
- Продуктивність і довготривалі soak-тести, окрім випадків, прямо вказаних у PRD.
- Сертифікація, EMC, реальне морське середовище.

## 3. Підхід і рівні тестування

| Рівень | Що | Як |
|---|---|---|
| Smoke | Boot, version, status, help | pytest, маркер `smoke` |
| Функціональний | Кожна вимога, позитив + негатив | pytest, маркер `functional` |
| Межовий (BVA) | Мін-1, мін, макс, макс+1 | параметризований pytest |
| Збереження (persistence) | Reboot / OTA | pytest, маркер `persistence` |
| Регресія | Повторний прогін усього на 2.3.0 | той самий набір (версія визначається з самого пристрою) |
| OTA | Успіх, rollback, помилки | pytest + локальний `ota_server.py`, маркер `ota` |
| Managed Wi-Fi | AP down, upstream/WAN down, recovery | `framework/drivers/managed_ap.py`, маркер `managed_wifi`, прапорець `--run-managed-wifi` |
| HIL: кнопки | K1–K4 фізично, з точною тривалістю press/hold/комбінацій | Arduino Nano, маркер `hil_stage`, прапорець `--run-hil` |
| Фізичні (ручні) | LED, діод, реле, HC-SR04 (кнопки автоматизовані через HIL) | чек-лист, evidence — логи, за потреби фото/відео |
| Exploratory / security | Приховані команди, секрети | ручний + `strings` по бінарнику |

### Принципи

1. **Автоматизуємо те, що вимірюється по UART** (коди помилок, межі, формати, NVS). **Фізичне перевіряємо очима** — PRD цього вимагає явно.
2. Кожен тест-кейс має ID вимоги; кожна вимога — принаймні один кейс (`docs/traceability.md`).
3. Кожен баг відтворюється ≥3 рази, до звіту додається лог.
4. Перед кожним тестом відомий початковий стан (reboot → logout → NORMAL), інакше результати не порівнюються.
5. Пароль Wi-Fi у логах замінюється на `***` автоматично (драйвер).
6. AP loss і upstream loss перевіряються окремо: вимкнення `SENTRY-HIL` не можна трактувати як WAN loss.

## 4. Ризики і пріоритети

Тестуємо за ризиком: спершу те, де помилка найдорожча.

| # | Ризик | Вплив | Імовірність | Що перевіряємо насамперед |
|---|---|---|---|---|
| R1 | Брак меж діапазонів (off-by-one) | середній | висока | Усі BVA: distance 1–20, health 10–300, pulse 100–10000 тощо |
| R2 | Втрата даних у NVS після reboot/OTA | високий | середня | OTA-10, AU-5, RL-2, LM-7 |
| R3 | OTA brick / нестабільний rollback | високий | низька | OTA-7/8/9 |
| R4 | Обхід автентифікації / привілеїв | високий | середня | AC-1, AU-2c, AU-6, RES-* |
| R5 | Регресії у 2.3.0 («виправлення» повертають баги) | високий | середня | NFR-1, повторний прогін |
| R6 | Хибний/пропущений ALARM у Guard | високий | середня | GD-2…GD-5, особливо GD-4b |
| R7 | Небезпечний стан реле/діода | середній | середня | RL-1, RL-7, AL-5 |
| R8 | Зависання на некоректному вводі | середній | середня | NFR-4 fuzz |
| R9 | Секрети в логах/бінарнику | високий | висока | RES-1…4 |

## 5. Критерії входу / виходу

**Вхід:** плата прошита `v2.1.0` після `erase-flash`; boot log містить `fw v2.1.0` і `ready. state 1 NORMAL`; AP `SENTRY-HIL` активний; upstream `<upstream>` підключений через USB dongle; всі кнопки/датчик/реле/діод підключені та перевірені.

**Вихід:**
- усі P1-кейси виконані на 2.1.0 і частково на 2.3.0;
- усі знайдені баги описані, відтворені ≥3 рази;
- матриця багів і трасабіліті заповнені;
- прийнято рішення GO / NO-GO / CONDITIONAL.

## 6. Критерії GO / NO-GO для 2.3.0 → stable

| Вердикт | Умова |
|---|---|
| **NO-GO** | Є хоча б одне: критичний функціональний баг; регресія P1-функціоналу з 2.1.0; ризик brick при OTA / нестабільний rollback; втрата даних після OTA; обхід автентифікації; хибна поведінка Guard ALARM; незрозумілий reset loop |
| **CONDITIONAL** | Є лише нескритичні баги (P2/P3), що не зачіпають безпеку і дані, є план виправлення та погодження |
| **GO** | Всі P1 зелені, немає регресій, OTA-цикл працює, відомі проблеми — лише косметичні |

Severity: Blocker / Critical / Major / Minor / Trivial. Priority: P1–P3 (за терміновістю виправлення).
