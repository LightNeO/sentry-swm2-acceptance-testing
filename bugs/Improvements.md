# Знахідки та спостереження (не баги проти PRD)

Тут зібрано те, що не порушує конкретну вимогу PRD, але варто врахувати до релізу: безпека (RES-1…5) і спостереження (OBS-01…03).

## OBS-01 — `reconnect` після `reboot` повертає `E101 wrong password`, хоча пароль правильний

| | |
|---|---|
| Версія | 2.1.0; у стендових прогонах на 2.3.0 (`logs/hil/`) перший `reconnect` після hard reset помилки E101 не давав, але окремо не перевірялось |
| Вимога | WF-2 (E101 = неправильний пароль; E108 = інша причина), WF-3 (`reconnect`) |
| Статус | **Не підтверджено як баг прошивки.** Середовище: телефонний хотспот, WPA3-SAE |

**Спостереження** (скрипти в scratchpad, 4 серії):

| Серія | Дія | Результат |
|---|---|---|
| 1 | hard reset (RTS) → `reconnect`, ×8 | OK/E101 чергуються, 4 і 4 |
| A | кілька `reconnect` підряд без reset | 4/4 OK |
| B | hard reset → пауза 15 с → `reconnect` ×4 | чергування E101/OK |
| C | `disconnect` → hard reset → `reconnect` ×4 | чергування E101/OK |
| D | hard reset → `reconnect`; на E101 одразу повтор без reset ×6 | 5 з 6 перший E101, **повтор завжди OK** |
| E | команда `reboot` (soft) → `reconnect` ×6 | 6/6 OK |

**Висновок:**
- `reconnect` як функція справний (A, E).
- Збій пов'язаний саме з жорстким скиданням (RTS), яке не завершує Wi-Fi чисто. Повтор без reset вирішує проблему.
- Пауза (B) і попередній `disconnect` (C) не допомагають.

**Чому це може бути проблемою продукту:** втрата живлення — реалістичний сценарій. Після неї пристрій відповідає `E101 wrong password`, хоча пароль не змінювався, і це вводить оператора в оману. Мало б бути E108 або повторна спроба.

**Що не перевірялось:** реальний power cycle (відключення USB) замість RTS і інша точка доступу (роутер замість телефонного хотспота), тому поведінка не оформлена як баг прошивки і може бути особливістю хотспота.

**Вплив на стенд:** `ensure_wifi` повторює `reconnect` до 3 разів, але тільки після E101; повтор записується в транскрипт. Базовий reset між тестами робиться командою `reboot`, а не RTS.

## RES-1 — Прихована команда `selftest`

| | |
|---|---|
| Версія | 2.1.0 |
| Статус | Підтверджено, сама по собі не є вразливістю |

Команда `selftest` відсутня в `help`, але працює без debug-доступу (лише `[login]`). Виводить короткий самотест підсистем:

```text
=== SWM-2 selftest ===
  [PASS] nvs        101/756 entries used
  [PASS] memory     257 KB free
  [PASS] temp       32.6 C
  [PASS] link       rssi -28 dBm
  [PASS] internet   ok
  [PASS] time       NTP synced
  [PASS] sonar      9.2 cm
  [PASS] valve      GPIO8 readback matches
  [PASS] buttons    released
  [PASS] firmware   v2.1.0 valid
=== 10 passed, 0 failed ===
```

Сама команда безпечна (лише читання стану), але її відсутність у `help` суперечить принципу, що оператор має бачити повний список доступних команд. Класифікація: інформаційна знахідка, не вразливість.

## RES-2 — Прихована команда `factory reset confirm` (потребує debug-доступу)

Стирає NVS (профіль, Wi-Fi, усі налаштування лампи/реле/сонара/health). Відсутня в `help`. Захищена рівнем `[debug]` (без `sudo` — `E004`). Ризик: якщо хтось отримає debug-доступ (а шлях до нього описано в RES-4), ця команда дає змогу приховано скинути пристрій до заводського стану без фізичного доступу.

## RES-3 — `dev dump` показує пароль профілю у відкритому вигляді з NVS

Команда `dev dump` (потребує `sudo`) виводить увесь вміст NVS, включно з:

```text
auth     login    = qa_swm
auth     pass     = Pass1234
```

Пароль Wi-Fi у цьому ж виводі замасковано (`password = ***`), а пароль облікового запису користувача — ні. Це означає, що пароль зберігається в NVS відкритим текстом, а не хешем/солю.

**Severity:** High (зберігання облікових даних без хешування — класична вразливість).
**Вплив:** будь-хто з debug-доступом бачить реальний пароль користувача, а не лише факт його існування.

## RES-4 — Пароль `sudo` для debug-доступу витікає через сам boot log

Кожен boot log містить рядок:

```text
I (599) sentry: build tag: <base64-redacted>
```

Це base64 від рядка виду `sudo <пароль>` — готова команда з паролем для підняття debug-доступу. Прошивка сама називає це "debug account hint" (рядок знайдено серед текстових рядків бінарника: `[SENTRY] debug account hint: <base64>` — ще один base64-натяк, схоже, на зарезервований debug-логін).

**Severity:** Critical. Секрет для підвищення привілеїв друкується в консоль при кожному старті пристрою, без будь-якої автентифікації — досить відкрити UART. У поєднанні з RES-3 (паролі в NVS відкритим текстом) і RES-2 (`factory reset` після debug) це ланцюжок: підслухати UART → розкодувати base64 → `sudo` → повний debug-доступ → `dev dump` (реальний пароль користувача) або `factory reset confirm`.

## OBS-02 — `help`-текст для `distance calibrate` вводить в оману щодо скидання

`help` показує: `distance calibrate <cm> - calibrate by reference object ('reset')`. Формулювання читається так, ніби `reset` — аргумент до `calibrate` (`distance calibrate reset`), але насправді скидання — окрема команда `distance reset`. `distance calibrate reset` дає `E706 usage: distance calibrate <ref 5-300 cm>`, що додатково підтверджує: `calibrate` не приймає `reset` як аргумент.

**Статус:** не баг прошивки — функціонал (`distance reset`) працює коректно. Це зауваження до тексту `help`/PRD, не до поведінки.

## OBS-03 — `[DBG]` діагностика парсера не специфікована в PRD

У DEBUG (`state 2`) команди виводять рядок на кшталт `[DBG] cmd 'distance' args '' need 2` перед звичайною відповіддю. PRD обіцяє лише факт наявності «діагностики парсера (`[DBG] ...`)», без опису формату чи значення полів (`need N` тощо). Команда при цьому виконується нормально — рядок не є помилкою.

**Статус:** інформаційне, не баг. Немає конкретної вимоги PRD, якій цей текст міг би суперечити.

## RES-5 — `sudo` не має захисту від перебору паролів

| | |
|---|---|
| Версія | 2.1.0 (не перевірено на 2.3.0) |
| Статус | Підтверджено, 6/6 спроб без жодної реакції захисту |
| Severity | High |

**Кроки:** 6 разів поспіль `sudo <неправильний пароль>`.

**Результат:** кожна спроба — однаковий `E213 sudo: wrong password`, без лічильника спроб, без затримки, без блокування.

```text
attempt 1: E213 sudo: wrong password
attempt 2: E213 sudo: wrong password
attempt 3: E213 sudo: wrong password
attempt 4: E213 sudo: wrong password
attempt 5: E213 sudo: wrong password
attempt 6: E213 sudo: wrong password
```

**Порівняння з `login`:** AU-2b документує чітке правило для `login` — після 3 невдалих спроб аккаунт блокується на 30 с (`E210`/`E207`). Для `sudo` такого механізму немає зовсім, хоча підвищення привілеїв до `[debug]` — більш чутлива дія, ніж звичайний вхід.

**Посилення ризику:** у поєднанні з RES-4 (пароль `sudo` відкрито друкується в boot-логу у вигляді base64) захист від перебору однаково не є першою лінією оборони, але його відсутність — самостійна, незалежна від RES-4 вада. Навіть якби пароль не був у лозі, його можна було б підбирати необмежено, не ризикуючи блокуванням.

**Докази:** `logs/research/sudo_brute_force_check.log`

**Класифікація:** знахідка безпеки (не порушення конкретного пункту PRD — AU-2b стосується лише `login`), тому не оформлена як `BUG-0xx`.

## OBS-04 — OTA з кастомного джерела перевстановлює ту саму версію

`ota update` з налаштованим локальним сервером (`ota server http://<IP>:8000/fw7/`) на поточній версії 2.1.0 відповів `W409 same version v2.1.0 - reinstalling` і почав качати образ (обірвано на 40% для іншого тесту). OTA-4b каже, що має бути `already up to date`; на стандартному сервері (GitHub) це працює правильно (TC-OTA-06).

**Статус:** не оформлено як баг — стосується лише шляху з кастомним сервером, повний прогін до кінця не виконувався. Лог: `logs/v2.1.0/manual/group6_ota.log`.

Те саме на 2.3.0: `ota url <файл>` з образом тієї самої версії дає `W409 same version v2.3.0 - reinstalling` і повне завантаження (`logs/v2.3.0/manual/partE_ota_bad_images.log`). Тобто поведінка не залежить від команди, лише від того, що джерело не GitHub.

## OBS-05 — `E401` (друге OTA під час першого) недосяжний з консолі

Поки йде завантаження, консоль не приймає команд (ввід не обробляється до кінця OTA), тому перевірити `E401 оновлення вже йде` (OTA-9, TC-OTA-22) через UART неможливо. Код, найімовірніше, спрацьовує за іншого шляху запуску OTA (наприклад, з кнопки або фонового потоку), але з консолі цього не видно.

**Статус:** не баг, обмеження способу перевірки; TC-OTA-22 позначено N/A, поведінку прийнято як очікувану. Лог: `logs/v2.3.0/manual/partE_ota_bad_images.log`.

## OBS-06 — без інтернету `ota check` дає `E411` або `E402` залежно від того, чи вже знає прошивка про відсутність інтернету

| | |
|---|---|
| Версія | 2.3.0 |
| Вимога | OTA-9: «E402 сервер недоступний … E411 немає інтернету» |
| Статус | З'ясовано: поведінка відповідає PRD, не баг. PRD лише не описує, коли саме який код |

**Умови:** плата підключена до iPhone-хотспоту (rssi −32), на телефоні вимкнено мобільні дані, `ota check`.

**Результат:** після ~9 с очікування `E402 cannot reach OTA server (stable.txt)`.

**Спостереження:** `E411` не вдалося отримати в жодному сценарії: ні без інтернету, ні при обриві Wi-Fi під час завантаження (там `W110` + `E410`), ні без Wi-Fi (там `E002`). Або `E411` у цій прошивці спрацьовує за умови, якої PRD не описує, або `E402` перекриває його.

**Повторно (керований AP, `logs/hil/`):** при вимкненні AP `ota check` дає `E402` (поки прошивка ще не помітила втрату зв'язку, до `W110`) або `E002` (після `W110`). Для upstream down — `E402`. `E411` знову не з'явився; попередні твердження в документах, що AP down дає `E411`, були помилковими й виправлені.

**Остаточно (керований AP, `logs/hil/SUMMARY.md`, 3 прогони TC-OTA-25 (б)):** `E411` таки з'явився:
`E411 no internet - OTA server unreachable`. Правило, яке збігається у всіх трьох прогонах:

| `status`: internet | `ota check` | час відповіді |
|---|---|---|
| `NO` (прошивка вже знає, що інтернету немає) | `E411 no internet - OTA server unreachable` | миттєво (0,3 с) |
| `OK` (ще не помітила) | `E402 cannot reach OTA server (stable.txt)` | після тайм-ауту (~10 с) |

Тому попередні висновки «`E411` не з'являється ніколи» були хибними: у ручному тесті (iPhone без даних) прапорець ще
був `OK`, і ми бачили `E402`. Рекомендація залишається до PRD: описати обидва коди й умову. Логи:
`logs/v2.3.0/manual/partE_ota_bad_images.log`, `logs/hil/SUMMARY.md`.
