# BUG-008 — `alert ack <id>` не підтверджує перший алерт у списку

| Поле | Значення |
|---|---|
| Версія, де знайдено | 2.3.0 (функціонал з'явився лише в цій версії, в 2.1.0 відсутній) |
| Severity | Major |
| Priority | P2 (Medium) |
| Вимога PRD | AL-3b: «`alert ack <id>` — підтвердити **саме alert з цим id** (немає — E851, вже підтверджено — W852)» |
| Тип | Логічна помилка (off-by-one за позицією в масиві) |
| Відтворюваність | 3/3 (три незалежні запуски з чистим списком алертів) |

## Передумови
- DUT 2.3.0, `login` виконано, список алертів порожній (`alert ack all` → `alert clear`).

## Кроки відтворення
1. `alert test info` → створюється алерт з якимось ID (напр. `#1`, `#7`, `#10` — конкретне число не має значення).
2. `alert list` → підтверджує, що алерт існує і позначений як непідтверджений (`*`).
3. `alert ack <той самий ID>`.

## Очікуваний результат
Алерт підтверджується: `[CIC] #<id> acknowledged`, у `alert list` зникає позначка `*`.

## Фактичний результат
Команда відповідає `E851 no alert #<id>`, хоча той самий `alert list` щойно показав цей алерт як існуючий:

```text
> alert test info
I (15520) sentry: [CIC #1 INFO] test: test alert
> alert list
I (16690) sentry: [CIC] 1 alerts, 1 unacknowledged:
  #1   12:07:41 INFO     * test    test alert
> alert ack 1
E (17810) sentry: E851 no alert #1
```

## Чому це саме «перший у списку», а не «ID = 1»

Перевірено на трьох алертах одразу після очищення списку:

```text
alert test info    -> #1
alert test warning -> #2
alert test info    -> #3

alert ack 2  -> [CIC] #2 acknowledged     (OK)
alert ack 3  -> [CIC] #3 acknowledged     (OK)
alert ack 1  -> E851 no alert #1          (FAIL)
```

Також відтворено в межах повного регресійного прогону (`framework/tests/functional/test_alert.py`), де через наскрізний (ніколи не скидається) лічильник ID перший алерт конкретного тесту мав ID `7` і `10` у різних прогонах — і так само не підтверджувався (`E851 no alert #7`, `E851 no alert #10`), тоді як ack за іншими ID у тому ж списку працював. Отже дефект прив'язаний не до числового значення ID, а до **позиції алерта в поточному списку** (перша позиція). Ймовірна причина — помилка off-by-one у пошуку (цикл починається з другого елемента); коду прошивки немає, тому це припущення за поведінкою.

- Автотест: `framework/tests/functional/test_alert.py::test_ack_by_id_acknowledges_exactly_that_one` (TC-AL-05)

## Вплив
Користувач не може цілеспрямовано підтвердити конкретний найстаріший активний alert командою `alert ack <id>`, що суперечить документованій поведінці AL-3b і ускладнює роботу з Alert center, коли потрібно підтвердити саме старий запис, а не останній (`alert ack` без ID підтверджує лише останній непідтверджений, AL-3a).
