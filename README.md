# SENTRY SWM-2 — приймальні випробування прошивки ESP32

Повний цикл тестування прошивки для embedded-пристрою: від розбору вимог і тест-плану до автоматизації по UART, ручного тестування на реальному залізі, OTA-сценаріїв і фінального вердикту GO/NO-GO.

## DUT

**SENTRY SWM-2** — навчальна модель гідроакустичного модуля на базі ESP32-S3 DevKit. Консольний пристрій з UART-керуванням (115200 8N1): Wi-Fi і акаунт з логіном, активний сонар на HC-SR04, реле-клапан з індикаторним діодом, RGB-лампа, чотири кнопки. У версії 2.3.0 додались охоронна зона (Guard) і центр сповіщень (Alert center). Дві версії прошивки під тестом: 2.1.0 (stable) і 2.3.0 (beta) — завдання було вирішити, чи можна 2.3.0 перевести в stable.

Повний опис функціоналу — `fw_7/PRD.md`

## Етапи проєкту

### Етап 1. Покриття DUT

Початкова версія проєкту була присвячена самому DUT — прошивці SENTRY SWM-2 на ESP32-S3. Спочатку були розібрані вимоги PRD, складені тест-план і тест-кейси, а потім виконані:

- автоматичні UART-тести команд, станів, меж параметрів, акаунта, OTA та безпеки;
- ручні перевірки того, що не можна було підтвердити через UART: LED, діод, фізичне реле, сонар, кнопки та поведінка на реальному стенді;
- порівняння прошивок 2.1.0 і 2.3.0;
- оформлення багів, ручних логів, traceability та фінального GO/NO-GO verdict.

На цьому етапі автоматизація керувала ESP32 через UART, але фізичні кнопки ще натискалися людиною.

### Етап 2. Arduino HIL для кнопок

Друга фіча — початковий HIL-стенд на Arduino Nano. Nano замінив ручне натискання K1–K4 і почав подавати фізичні стимули з точною тривалістю:

- коротке натискання кнопок;
- утримання K4 для PANIC;
- одночасні комбінації K3+K4 і K4+K1;
- перевірка переходів NORMAL/DEBUG/VERBOSE/EMERGENCY;
- повторювані сценарії без людської похибки.

Arduino відповідає тільки за stimulus. Python/pytest через UART перевіряє реакцію ESP32. Так були автоматизовані кнопкові manual-кейси, а LED, фізичне реле, діод і sonar залишилися `A+M`, якщо для них потрібне додаткове спостереження.

Деталі етапу: `docs/hil_button_stage.md`.

### Етап 3. Керований Wi-Fi HIL

Третя фіча — керування мережею самого HIL-стенду. У ноутбуці використовуються два Wi-Fi адаптери:

```text
USB dongle wlp0s21f0u2 -> upstream NeO
built-in wlp1s0       -> AP SENTRY-HIL для ESP32
```

Через NetworkManager і dnsmasq тестовий агент може окремо керувати:

- втратою AP/Wi-Fi association;
- втратою upstream/WAN при активному AP;
- відновленням AP і DHCP;
- доступністю OTA server через тестову мережу.

Це дозволило перевести частину Wi-Fi та OTA manual-кейсів у керовані автотести: connect/reconnect, scan, `net`, ping, time, AP loss, recovery, OTA server faults і перевірку збереження мережевого стану.

Керування мережею описане в `docs/managed_ap.md`, controller знаходиться в `framework/drivers/managed_ap.py`, а тести — у `framework/tests/wifi/`.

### Результат

У результаті вийшов не окремий скрипт для Arduino і не набір розрізнених тестів, а єдиний acceptance-testing framework із HIL-стендом:

```text
pytest
  -> UART driver -> ESP32 DUT
  -> Arduino Nano -> фізичні кнопки K1-K4
  -> NetworkManager/dnsmasq -> керований Wi-Fi AP/WAN
  -> transcripts, logs, traceability, bug evidence
```

Базові DUT-тести, Arduino HIL і managed Wi-Fi HIL запускаються окремими стадіями. Це дозволяє запускати звичайні тести без стенду, а фізичні сценарії вмикати явно через `--run-hil` або `--run-managed-wifi`.

## Процес тестування

1. **Розбір вимог.** PRD → 139 атомарних вимог з ID (`docs/requirements.md`).
2. **Тест-документація.** 222 тест-кейси з граничними значеннями на кожен числовий параметр (`docs/test_cases.md`), тест-план з аналізом ризиків (`docs/test_plan.md`), матриця трасабіліті, яка генерується скриптом з вимог + кейсів + результатів - щоб не розходилась з реальністю (`docs/traceability.md`, `framework/tools/gen_traceability.py`).
3. **Фреймворк автотестів** на pytest: драйвер для UART-консолі, парсер протоколу, фейковий транспорт для юніт-тестів без заліза (237 тестів разом, `framework/`).
4. **HIL-стадія для кнопок.** Arduino Nano фізично натискає K1–K4 із заданою тривалістю, а pytest одночасно перевіряє відповідь ESP32 через UART. Це окрема стадія і не запускається разом зі звичайними тестами без прапорця `--run-hil`.
5. **Керована Wi-Fi-стадія.** USB-донгл підключає ноутбук до upstream-мережі `NeO`, а вбудований адаптер роздає `SENTRY-HIL` для ESP32. NetworkManager і dnsmasq дають змогу окремо вимикати AP або upstream під час Wi-Fi/OTA тестів.
6. **Тестування 2.1.0** — повністю: автотести + ручний чек-лист на все, що треба бачити очима (LED, діод, фізична поведінка реле). Кнопкові сценарії тепер мають окремий HIL-шар.
7. **OTA 2.1.0 → 2.3.0**, перевірка збереження налаштувань, тестування нового функціоналу (Guard, Alert center, кнопка K4) і повторення всього старого як регресії.
8. **OTA fault-injection** — локальний сервер з навмисним обривом завантаження, повільним каналом з реальним вимкненням Wi-Fi, навмисно зламаною збіркою для перевірки автоматичного rollback.
9. **Дослідницьке тестування безпеки** — приховані команди, пошук секретів, перевірка захисту від перебору паролів.
10. **Вердикт** з обґрунтуванням за заздалегідь визначеними критеріями GO/NO-GO (`docs/verdict.md`).

## Результати

- **10 підтверджених багів**, 5 виправлено між версіями (у тому числі Critical — пароль не зберігався після reboot), 3 лишились, 2 нових з'явились разом з новим функціоналом 2.3.0 (Alert center і Guard). Повна таблиця — `bugs/BUG_MATRIX.md`, кожен баг — окремий репорт у `bugs/`.
- **237 автотестів**. Усі 139 вимог мають тест-кейси (222 кейси), результат записано для 161 із них; решта — кейси, які я не встиг виконати (прогалини описані у `docs/verdict.md`, розділ 5).
- **Знахідки безпеки**: пароль для debug-доступу друкується в boot-лозі base64, пароль користувача зберігається в NVS відкритим текстом, `sudo` не має захисту від перебору на відміну від звичайного логіну (`bugs/Improvements.md`).
- **Нуль випадків "зацеглення" пристрою при OTA** — перевірено навіть навмисно зламаною збіркою, пристрій сам відкотився на робочу версію без втручання.

**Вердикт: NO-GO до виправлення BUG-010.** Guard видає хибний ALARM (лічильник неправильних PIN не скидається) — це прямий пункт NO-GO з тест-плану. OTA, rollback, дані й автентифікація в порядку, ризику для заліза не знайдено. Після виправлення цього багу вердикт — CONDITIONAL GO (лишаються три дрібні дефекти і пункт безпеки).  з усіма критеріями — `docs/verdict.md`.

## Стек і інструменти

Python, pytest, pyserial, esptool. Власний UART-драйвер з парсером протоколу і фейковим транспортом для тестування самого фреймворку без заліза. Локальний HTTP-сервер для емуляції збоїв OTA. Mermaid-діаграма теоретичного HIL-стенда з логічним аналізатором і стимуляторами — `docs/hil_stand.md`.

## Апаратна автоматизація кнопок

У цій версії додано HIL-стимулятор на Arduino Nano для K1–K4. Nano отримує команди через USB serial і фізично замикає входи кнопок ESP32 на GND. Python-драйвер керує Nano, а `SwmDevice` читає фактичну відповідь DUT через UART.

### Підключення

| Arduino Nano | ESP32-S3 | Кнопка |
|---|---|---|
| A2 через 1 кОм | GPIO41 | K1 / beacon |
| A3 через 1 кОм | GPIO40 | K2 / valve |
| A4 через 1 кОм | GPIO39 | K3 / sonar |
| A5 через 1 кОм | GPIO38 | K4 / Guard/Alert |
| GND | GND | спільна земля |

Прошивка Nano працює в режимі open-drain: натиснення — `OUTPUT/LOW`, відпускання — `INPUT/high-Z`. Nano не подає `HIGH` на GPIO ESP32. Для постійного стенду все одно бажані оптопари або NPN/open-collector каскади, оскільки Nano працює з 5 V, а ESP32 — з 3.3 V.

Детальна схема, протокол і застереження описані в [`hardware/button_stimulator/README.md`](hardware/button_stimulator/README.md) та [`docs/hil_button_stage.md`](docs/hil_button_stage.md).

Керування Wi-Fi стендом описане в [`docs/managed_ap.md`](docs/managed_ap.md). Код контролера — `framework/drivers/managed_ap.py`.

### Команди Nano

UART Nano: `115200 8N1`.

```text
PING
STATUS
PRESS K1 150
HOLD K4 1500
HOLD K3+K4 2200
STOP
```

Після дії Nano повертає підтвердження, наприклад `OK K3+K4 2200`. Діапазон тривалості — 1–10000 мс. Для комбінацій у HIL-тестах використовується 2200 мс: на точній межі 2000 мс ESP32 іноді встигає побачити release раніше, ніж розпізнає hold.

### Прошивка Nano

Для цієї плати з CH340 і signature `ATmega328P` використовується профіль із новішим avrdude:

```bash
cd hardware/button_stimulator
pio run -e nanoatmega328avrdude8 --target upload --upload-port /dev/ttyUSB0
```

Перевірити Nano окремо від ESP32 можна так:

```bash
pio device monitor -p /dev/ttyUSB0 -b 115200
```

Очікувані відповіді: `PING` → `PONG`, `STATUS` → `READY`.

### Запуск HIL-стадії

У поточному стенді Arduino — `/dev/ttyUSB0`, ESP32 — `/dev/ttyUSB1`. Перед запуском краще перевірити порти через `pio device list` або `/dev/serial/by-id`.

```bash
export BUTTON_STIM_PORT=/dev/ttyUSB0
export SWM_PORT=/dev/ttyUSB1

cd framework
python -m pytest tests/hil -m hil_stage --run-hil --keep-logs
```

Без `--run-hil` фізичні тести пропускаються, тому звичайні `unit` і `functional` прогони не намагаються керувати Arduino.

Managed Wi-Fi stage запускається окремо, бо може тимчасово вимкнути AP або upstream:

```bash
export HIL_AP_CONNECTION=SENTRY-HIL
python -m pytest tests/wifi -m managed_wifi --run-managed-wifi --keep-logs
```

`TC-WF-01`–`TC-WF-07` і `TC-WF-10`–`TC-WF-17` перевіряють connect/reconnect lifecycle через `SENTRY-HIL`. `TC-WF-18` перевіряє AP loss і recovery. `TC-OTA-23/25/26/31` перевіряють network faults та OTA server profile. `TC-OTA-16` поки partial: AP fault автоматизований, slow OTA fixture ще не доданий. Перевірки unsupported security, DHCP/no-DHCP, слабкого сигналу та NTP fault не входять до поточного scope.

### Що тепер автоматизовано

Окрема стадія містить тести `HIL-BTN-01`…`HIL-BTN-07`, `HIL-BTN-09`, `HIL-BTN-10` та `HIL-GD-07`:

- K1: натискання і UART-подія Beacon;
- K2: натискання, Valve і pulse із завершенням;
- K3: запуск і зупинка active pinging;
- K4: підтвердження Alert;
- K3+K4: перехід у VERBOSE;
- K4+K1: заборона EMERGENCY із NORMAL/DEBUG та вхід із VERBOSE;
- K1–K4 без login: `E003`;
- K1–K3 у EMERGENCY: `E005` для 2.1.0;
- K4 hold у Guard: PANIC/ALARM, якщо перед стендом є потрібний об’єкт для sonar;
- Guard `TC-GD-11/12` і Alert `TC-AL-11` уже мають окремі UART-автотести у `framework/tests/functional/`.

Класифікація в `docs/test_cases.md` оновлена так:

- `A` — stimulus і перевірка повністю автоматичні;
- `A+M` — UART-частина автоматична, але LED, фізичне реле, sonar або electrical debounce ще треба перевіряти вручну;
- `M` — повністю ручна частина, наприклад візуальні RGB-патерни без камери.

### Що все ще manual

Arduino не доводить сам по собі, що реле фізично клацнуло, LED має правильний колір або HC-SR04 бачить потрібну відстань. Для повної автоматизації цих частин потрібні logic analyzer для GPIO4/GPIO8, камера/фотодатчик для LED та окремий distance stimulator. Тому `TC-BTN-01`, `TC-BTN-02`, `TC-BTN-03`, `TC-BTN-04`, `TC-BTN-08`, `TC-GD-07` і `TC-AL-11` залишаються `A+M`.

Детальна карта того, що перенесено з manual у HIL, знаходиться в [`docs/hil_button_stage.md`](docs/hil_button_stage.md). Старі ручні логи не видалялись: вони залишаються доказом початкового прогону та джерелом очікуваних UART-подій.
